# 기술 블로그 스타일 가이드

이 스타일 가이드는 기술 블로그(`kdevkr.github.io`)의 일관된 품질과 가독성을 유지하기 위한 상세 지침을 제공합니다.

## 1. Frontmatter 규격
모든 포스트 시작 부분에 다음과 같은 YAML 형식을 작성해 주세요.

```yaml
---
title: 포스트 제목
date: YYYY-MM-DD'T'HH:mm+09:00
description: 한 줄 요약 (목록·OG 메타용, 80~140자 권장)
tags:
  - 키워드1
  - 키워드2
---
```
# [포스트 제목]

- **문서 제목 (H1)**: 모든 포스트는 YAML Frontmatter 바로 아래에 **`# 포스트 제목`** 형식을 반드시 포함해야 합니다.
- **date**: 초 단위를 제외한 **`YYYY-MM-DD'T'HH:mm+09:00`** 형식을 엄격히 준수해 주세요.
- **description**: 글 목록(`/posts`)과 SNS 공유(OG/Twitter) 미리보기에 노출되는 한 줄 요약입니다. 제목과 중복되지 않게 글의 결론·맥락을 80~140자로 적어 주세요.
- **tags**: 검색 편의를 위해 관련 키워드 2~4개를 YAML 배열 형식으로 작성해 주세요.

## 2. 문서 구조 및 헤더
- **H1 (`#`)**: 페이지 제목으로만 사용하며, 문서당 **단 하나**만 존재해야 합니다.
- **계층 구조**: 큰 주제는 `##`, 하위 주제는 `###`을 사용하여 정보를 단계적으로 전달해 주세요.
- **도입부**: 문서 제목 바로 아래에 해당 글의 목적과 요약된 내용을 1~2문장으로 작성해 주세요.
- **구분선 (`---`) 사용 제한**: `##` 이나 `###` 와 같은 섹션 헤더 바로 위에는 **`---` (가로 실선)** 을 두지 마세요. VitePress 테마가 제목 하단에 구분선을 자동으로 렌더링하기 때문에, 본문에 구분선을 넣으면 불필요한 이중 구분선이 생겨 레이아웃이 지저분해집니다.
- **요약/마치며 섹션 금지**: 글의 하단에 상투적이거나 형식적인 **`마치며`**, **`요약`**, **`정리`** 등의 결론용 섹션(H2 헤더)을 두지 마세요. AI가 생성한 듯한 불필요한 서술을 방지하고 핵심 중심의 깔끔한 종결을 위해, 마지막 실무적/기술적 섹션 작성 후 글을 자연스럽게 바로 마쳐야 합니다.
- **참고 자료 섹션 금지**: 글 하단에 **`참고 자료`**, **`References`**, **`출처`** 등 외부 링크만 모아둔 별도 섹션(H2 헤더)을 두지 마세요. 인용·출처는 본문 안에 인라인 링크(`[텍스트](URL)`)로 직접 노출하여 문맥과 함께 검증할 수 있도록 합니다. 본문에 자연스럽게 녹일 자리가 없다면, 그 링크는 굳이 글에 포함하지 않는 것이 좋습니다.



## 3. 이미지 및 미디어 관리
- **저장 경로**: `public/images/posts/[포스트파일명]/` 디렉토리에 저장해 주세요.
- **참조 경로**: 마크다운에서 이미지를 참조할 때는 `public`을 제외한 **`/images/posts/[포스트파일명]/[번호].png`** 형식을 사용해야 합니다. 로컬 절대 경로(`file:///`)나 `public` 접두사를 포함하지 않도록 주의하세요.
- **파일명**: `001.png`, `002.png`와 같이 세 자리 숫자로 순차적으로 지정해 주세요.

## 4. 코드 블록
- **언어 명시**: 모든 코드 블록에는 해당 언어(예: `ts`, `go`, `yaml`, `bash`)를 명시하여 구문 강조(Syntax Highlighting)가 작동하도록 해주세요.
- **타이틀 추가**: 코드 블록 상단에 파일명이나 제목을 표시할 때는 ` ```언어 [타이틀] ` 형식을 사용합니다. (예: ` ```json [settings.json] `)
- **설명**: 코드에 대한 핵심적인 설명은 블록 위나 아래에 텍스트로 보완해 주세요.

## 5. 한국어 경어 및 톤앤매너
- **기본 말투 (해요체)**: 블로그 본문은 독자에게 친근하고 정중한 **해요체** (`~해요`, `~이에요`, `~했어요`)를 기본으로 사용해 주세요.
- **공식 문체 (합쇼체) 유지 대상**: 다음과 같은 맥락에서는 **합쇼체** (`~합니다`, `~입니다`, `~않습니다`)를 사용해 주세요.
  - **계약서 특약 사항**: 실제 계약서에 기재되는 조항은 `-한다`, `-않는다` 형식의 계약 문체를 사용해 주세요.
  - **법령 조문 직접 인용**: 주택임대차보호법, 개인정보보호법 등 법조문을 인용할 때는 원문 문체(`~할 수 없습니다` 등)를 유지해 주세요.
  - **공공기관 공식 안내문 인용**: 정부 또는 공공기관의 공식 문서를 직접 인용하는 경우 원문 문체를 유지해 주세요.
- **명사형 스펙 목록**: 사양·조건·기능처럼 사실을 나열하는 목록(예: 매물 정보, 기술 스펙, 설정 값 등)은 동사형 어미를 생략하고 명사형으로 간결하게 작성해 주세요.
  - 예: `2021년 준공, 내부 컨디션 최상, 외부 주차 가능` (O) / `2021년 준공되었습니다` (X)
- **어조 혼용 금지**: 같은 문장 또는 blockquote 안에서 해요체와 합쇼체를 혼용하지 마세요.
- **핵심과 간결함**: 글은 절대 장황하지 않게, 핵심 개념과 필요한 코드 중심으로 **극도의 간결함**을 유지하며 작성해 주세요.
- **어휘**: 지나치게 어려운 전문 용어보다는 이해하기 쉬운 표현을 권장하며, 필요한 경우 용어 설명을 추가해 주세요.
- **맞춤법**: 작성 후 문장이 매끄러운지, 맞춤법에 오류가 없는지 다시 한번 검토해 주세요.

## 6. 커밋 메시지 규칙
- 변경 사항을 전송할 때는 다음 규칙을 따라 주세요.
- **형식**: `title: [포스트 제목]`
- **예시**: `title: Antigravity AI 에이전트 연동 가이드`

## 7. 텍스트 서식
- **강조**: 중요한 키워드나 문구는 `**굵게**` 표현하거나, 필요에 따라 `==강조==` 스타일을 사용하여 시각적으로 부각할 수 있습니다.
- **렌더링 주의사항**: **굵게(`**`)** 또는 **강조(`==`)** 서식 바로 뒤에 특수문자나 한글 조사(는, 을, 를 등)가 붙으면 렌더링이 깨질 수 있습니다. 가급적 서식 뒤에 한 칸의 공백을 두는 것을 권장합니다.
  - 예: `**강조** 를 위해` (O) / `**강조**를 위해` (X)
